# Propuesta revisable de adaptación del adaptador
Revisión 1 · sin implementar · alcance de código pendiente de autorización.

## Límite observado en el código upstream fijado
scripts/run_opencode.py contiene MODEL=opencode-go/deepseek-v4.1-flash, valida agente primary survey-coder, crea sesión de ese agente y rechaza eventos de herramientas. Produce mapa/texto para el piloto estático; no es un ejecutor general de backend Python. verify_frontend.py verifica UI estática; pasar ese gate no prueba RAG/grafo/SQLite. La versión CLI soportada es 2.0.32. Estas son observaciones de código; no se ejecutó el adaptador en este proyecto.

## Cambios propuestos antes de código
1. Perfil de ejecución versionado: lenguaje/runtime, project_kind python_agent, agent/model/variante explícitos y allowlist; separar modelo coder/app. Reemplazar valores hardcodeados solo mediante perfil revisado, no flags arbitrarios sin contrato. Revisar check_plan y schemas para permitir runtime Python local con OpenRouter de app ya acordado y modelo app pendiente sin afirmar decisión humana falsa.
2. Conservar modo file-map sin herramientas para tareas pequeñas, si sirve, importando solo archivos exactos y revisados; no habilitar shell automáticamente. Si se requieren herramientas, diseñar interfaz broker y sandbox OS antes de cambiar el rechazo de tool events.
3. Runner Python separado: virtualenv/lock fijados, argv de validadores externos, scratch aislado, timeouts/descendientes/puertos, entorno mínimo sin secretos y dependencias disponibles sin instalación implícita. Tests/fixtures/control read-only para coder.
4. Gates backend: manifiesto de tests esperado y evidencias por candidato para recuperación, interrupciones humanas y persistencia. Añadir gate UI independiente solo si hay interfaz; no tratar Playwright como evaluación funcional completa.
5. Mantener autenticidad de aprobación, límites de reparación, journal y reconciliación; los contadores por invocación no bastan como historial durable. Importación de diffs/idempotencia y base Git deben estar resueltas antes de crear candidato.
6. Compatibilidad sin inferencia primero con CLI/servidor falsos y fixtures: modelo rechazado, auth faltante, herramientas prohibidas, contaminación de entorno, cambios fuera de allowlist, validador alterado, base obsoleta, timeout y reentrada sin duplicados. Después preflight real sin inferencia en aislamiento probado. Primera tarea real pequeña únicamente tras autorización de modelo, datos y presupuesto.

## Riesgos y gates
Parametrizar sin validar puede permitir fallback o permisos extra. Habilitar shell puede exponer host/credenciales o ejecutar dependencias maliciosas. Un lock no certifica compatibilidad por sí solo; validar backend con UI estática produce falsos positivos. Snapshots externos y hashes no son aislamiento OS ni firma humana.

No ejecutar scripts upstream, implementar esta propuesta, instalar paquetes, modificar repo compartido ni activar otro modelo como parte de este setup. Revisar con usuario/coordinador; una futura tarea de cambio al harness fijará archivos, pruebas y nueva versión, manteniendo este consumidor en su pin hasta migración explícita. No se propaga autoridad de otros pilotos.
