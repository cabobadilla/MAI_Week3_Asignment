# Gate HITL obligatorio antes de implementar UI

Para crear o cambiar materialmente una interfaz, dot debe presentar al usuario al menos dos opciones de mockup identificadas por opción y versión, antes de entregar implementación visual al coder. Mockups son prototipos aislados, nunca una modificación silenciosa del candidato aceptado. No elegir ni aceptar por silencio, tiempo transcurrido o juicio del coder.

Cada opción debe mostrar los estados relevantes del alcance en escritorio y móvil: flujo principal y resultado, errores/vacíos/carga si existen, y estados de puntero, teclado/foco cuando cambie la interacción. En un cambio acotado al encabezado de resultados no exigir rediseñar todo el producto. Capturas Playwright headless del prototipo y datos sintéticos, sin pantalla/CUA/navegador personal. Mantener foco visible para teclado; no borrar globalmente outlines para hacer atractivo un mockup.

Usar [registro de diseño](../templates/diseno-ui.md). Guardar en dot/ del consumidor: design ID/version, dos o más opciones, capturas y SHA-256, viewports/estados, opción elegida, fecha y referencia a la aprobación explícita del usuario. La spec referencia ese registro y su hash; la tarea cita la opción/versión aprobadas. La aceptación vincula requisitos visuales a estados/capturas y test IDs, incluyendo teclado. Las referencias quedan protegidas por el contrato congelado (spec y protected_files); no se inventan claves de opencode.json ni se cambia un contrato activo.

Precondición manual para ready/prepared/running de UI: aprobación explícita comprobable de una opción/version vigente y correspondencia con spec, tarea y aceptación. Si falta, es ambigua o el material cambió, estado design_review/blocked; el operador no debe invocar el coder para implementar UI. Construir mockups aislados sí está permitido para poder obtener esa decisión. Publicación y gasto siguen requiriendo su propia autoridad.

Cambiar layout, jerarquía, tipografía, colores, textos principales o interacción/foco de forma material invalida la aprobación para el nuevo trabajo: incrementar versión, presentar opciones actualizadas y pedir nueva aprobación antes de codificarlo. No reescribir la aprobación anterior ni afirmar que autoriza cualquier variante futura. Correcciones no visuales conservan su contrato; si hay duda material, dot documenta el alcance y obtiene aprobación nueva.

Estado real del control0.4: check_plan.py y run_opencode.py --plan comprueban decisión de destino, gateway, dos opciones desktop/móvil, selección/version vigente y hashes antes de invocar CLI para implementar. Pruebas offline negativas verifican que un plan UI sin aprobación ni siquiera llama al binario falso; cambio de mockup, versión obsoleta y opción única bloquean. El modo --preflight-only permite comprobar compatibilidad sin aprobar diseño, porque no implementa ni hace inferencia. El coordinador debe verificar autenticidad humana de approval_ref y proteger el plan; datos estructurados no prueban consentimiento por sí mismos. Esto no es un sandbox ni prohíbe invocar otro CLI por fuera del adaptador autorizado. Las regresiones son offline; no se lanzó otra inferencia GO real.

Los consumidores mantienen su versión fijada hasta migración explícita. El usuario decidió conservar el survey actual tal como está. Su candidato/preview0.3.1 siguen intactos; mockups separados se conservan como historial, sin aplicarlos ni inferir aprobación retroactiva. Cada ejecución registra retro incluso si el diseño queda bloqueado a la espera de elección.
