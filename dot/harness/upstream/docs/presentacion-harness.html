01 / El problema

El código por sí solo
no cierra una entrega

Una conversación con un agente puede producir software sin dejar claro qué se pidió, qué se probó y qué versión merece confianza.

01

Sin contrato

El alcance cambia y el agente puede interpretar “terminado” de otra forma.

02

Sin reproducción

Un test verde pierde valor si no sabemos qué código, pruebas y configuración usó.

03

Sin visibilidad

Al retomar, cuesta distinguir progreso, bloqueo y una ejecución todavía incierta.

El problema a resolver es la continuidad entre intención, ejecución y aceptación.

03 / Roles, empezando por dot

Dot coordina
y revisa el resultado

USUARIO / HUMAN IN THE LOOP

04 / Ejecución y validación

Un coder y un runner
con funciones distintas

La validación independiente del candidato es una ejecución de pruebas y una revisión dot. No supone otro agente de IA validador.

OPENCODE + DEEPSEEK FLASH GO

Implementar la tarea

El coder genera o repara código dentro del alcance permitido. El modelo observado en el piloto es opencode-go/deepseek-v4.1-flash.

RUNNER DETERMINISTA

Producir evidencia

Comprueba identidad e integridad y ejecuta pruebas protegidas. En UI usa Playwright y Chromium headless sobre una copia del candidato.

OpenRouterEs el runtime LLM de las apps que construimos. Es una decisión distinta del proveedor GO del coder.

05 / El proceso acordado

De la idea a la entrega

Cada paso produce un artefacto o una decisión que habilita el siguiente. Los fallos conservan su evidencia.

  1. 01

    Idea + destino

    Elegir local_simple con Wrangler local, Docker local o Cloudflare antes de arquitectura.

  2. 02

    Spec + criterios

    Alcance, arquitectura, aceptación y límites explícitos.

  3. 03

    Mockups + aprobación

    Para UI: mínimo dos opciones desktop/móvil, versión y hashes aprobados por el usuario.

  4. 04

    Tareas + OpenCode

    Una capacidad pequeña, entradas fijadas y un candidato identificable.

  5. 05

    Validación + revisión

    Pruebas, evidencia y revisión dot. Reparación acotada en una nueva ronda.

  6. 06

    Entrega + retro

    Versión aceptada, receta reproducible y lección saneada devuelta al harness.

Baseline compatible con Workers. Docker aporta aislamiento, no compatibilidad automática. Elegir destino no autoriza instalación ni publicación.

06 / Controles del harness

La aceptación pertenece
a un candidato concreto

El contrato une entradas, cambios permitidos, pruebas y resultados a una identidad verificable.

1

Pin de versión

Cada consumidor conserva su snapshot, versión y digest. Actualizar exige una decisión explícita.

2

Entradas protegidas

Spec, aceptación, tests y configuración quedan fuera del alcance editable del coder.

3

Gate + revisión

SHA, diff y hashes enlazan el candidato con el reporte. Dot puede rechazar un verde insuficiente.

Límite: prompts, permisos OpenCode y worktrees no crean una sandbox del sistema operativo. El aislamiento debe comprobarse por separado.

10 / Aprendizaje

Cada ejecución
devuelve una lección

Éxito, fallo, bloqueo o cancelación: dot conserva la retro en el consumidor y devuelve una copia saneada a lecciones/ del harness.

LECCIONES OBSERVADAS

Reducir fricción con evidencia

Specs por capacidades pequeñas. Control separado ante cambios de .DS_Store. Readiness, ubicación y sesión deben verificarse juntos.

Un timeout no prueba que el tamaño causó el fallo.

LÍMITES ACTUALES

Promover mejoras probadas

El flujo actual usa un file-map JSON sin herramientas nativas del coder. La autonomía sigue acotada.

Las propuestas se prueban antes de promover otra versión. Los pins activos se conservan.
